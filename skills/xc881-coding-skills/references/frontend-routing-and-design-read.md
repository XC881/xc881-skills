# Frontend Routing And Design Read

Use for visible UI creation/state/layout, responsive work, redesign/review,
assets or image-to-code. Explicitly nonvisual behavior repairs, backend, CLI,
config and documentation work load no frontend refs.

## Just-In-Time Escalation

Automatically load the next reference's missing rules when its concern is reached;
do not wait for another user request or handoff. Paths are from the skill root.

- Substantial new/reworked UI without a reusable system ->
  `./references/frontend-design-intelligence.md`, generate one project candidate.
- Otherwise unresolved visual/type/color/data/platform/UX decision -> the same
  reference, query only that concern.
- Code/layout/state work -> `./references/frontend-implementation-standard.md`;
  its layout/content/state/motion subrefs remain conditional.
- Supplied frame, image-to-code or unresolved art/assets ->
  `./references/frontend-image-reference-workflow.md`.
- Review/redesign, preservation risk or screenshot confirmation ->
  `./references/frontend-redesign-and-visual-qa.md`.
- Deliberate visual family, reusable block or advanced interaction ->
  `./references/frontend-pattern-catalog.md`.

Reuse valid in-context rules/evidence; a returning concern alone needs no reread.
Do not preload or reopen the set; known changes or lost rules need targeted reads.
Each branch continues to the next reached concern without restarting this router.

## Design Read

Inspect only the affected routes/components, tokens/styles, content/assets,
states, installed packages and platform conventions needed for the decision.
Account for audience/task/device, brand, accessibility, locale, supported themes
and identifiers that must remain stable. Reuse supplied evidence where valid.

For substantial new visual work, redesign or visual review, state one compact line:

```text
Surface / audience / task outcome / existing system or direction / key constraint
```

Do not add that ceremony to a narrow component change. Optional variance/motion/
density labels need a decision purpose, not permanent settings. Ask one blocking
question only if plausible directions materially change implementation; otherwise
infer from the actual brief and code.

## Authority And Scope

- Existing components/tokens/icon family, brand, legal content, supported themes
  and accessibility protections outrank generic aesthetics. Product UI prioritizes
  scanning/task flow; marketing variation is not a rule for operational grids.
- Mobile work follows platform flow, safe areas and native conventions. A named
  official system may require bounded official research; do not hand-copy it or
  add packages speculatively. A web aesthetic is not an official implementation.
- No new theme, identity, route, feature, font/motion library or asset pipeline
  merely for polish. Check manifests before dependency choices.
- Consume only an exact handed-off `dev-notes/design-system/.../MASTER.md` when
  needed, plus only named surface overrides. Never scan for one; a note is a
  target contract, not proof that it supersedes real code. Conflicts or missing
  queue scope/AC return to Requirement, not an invented redesign brief.
