# Taste Skill Integration

`xc881-coding-skills` integrates the transferable frontend capabilities audited
from `taste-skill` without adding another route target. Frontend references load
automatically, just in time, as active design work reaches their concern.

## Runtime Model

1. Coding reads the affected project surface and makes a compact Design Read for
   substantial visual work.
2. Existing brand, component system, platform convention, accessibility work,
   supported themes, content, and user scope take precedence.
3. Frontend routing starts the work. Only unresolved product/visual, type/color,
   data-display, mobile/platform, or concrete UX decisions load design
   intelligence. When implementation, image/reference, redesign/visual QA, or
   pattern work is reached, Coding automatically loads that next reference and
   continues without a user handoff. Non-frontend and explicitly nonvisual UI
   repairs load none.
4. Image generation and official-document research are bounded helpers. They do
   not become independent frontend skills or force a package installation.

## Runtime References

- `frontend-routing-and-design-read.md`: decide whether frontend design applies,
  establish the Design Read, then automatically load the next relevant reference
  when its concern is reached.
- `frontend-design-intelligence.md`: resolve one otherwise-unanswered design
  concern; it may request a gated `dev-notes/design-system` visual contract.
- `frontend-implementation-standard.md`: component architecture, responsive
  layout, real assets, states, accessibility, performance, and motion.
- `frontend-image-reference-workflow.md`: image-to-code, web/mobile visual
  references, and explicitly requested identity direction.
- `frontend-redesign-and-visual-qa.md`: audit/preservation and screenshot-level
  verification with an honest no-tool fallback.
- `frontend-pattern-catalog.md`: optional visual families and advanced patterns.

## Deliberate Non-Defaults

- Existing icon libraries win; when none exists, use Lucide for familiar icons.
- Motion needs a functional or narrative purpose and reduced-motion behavior.
- Dual themes, dark mode, fonts, system packages, visual assets, and large
  structural changes require actual task evidence.
- Generated images become repository assets only through the project asset
  pipeline. Fake screenshot divs, fake social proof, invented metrics, and
  copied identity assets are not acceptable substitutes.
- A durable visual contract is Requirement-owned under `dev-notes/design-system/`;
  Coding receives its exact path and never searches for one.
- Visual verification uses actual browser tooling when available. Otherwise
  Coding reports the unobserved visual boundary instead of claiming success.

The full source-level adopt/adapt/reject audit is kept in the corresponding
req-process evidence while implementation-facing behavior lives in the runtime
references above.
